## 不可以被默默改掉的決定

這些是有理由的刻意選擇，不是還沒做完的事。若之後有人（或另一次 desktop 比對）提議「對齊」，預設答案是否定，除非有新的實機證據。

| 決定 | 為什麼 |
| --- | --- |
| `metaLoginStatus()` 可以回 `null` → `'checking'`，**不要**照抄 desktop `afeb315` 的 `logged_out` | Meta 的 `loggedOutDetector` 是 `() => loginStatus() === false`，每個 `false` 都是 explicitlyLoggedOut，會繞過 `loginLossDelay`。照抄的話，meta.ai 只要在串流中途停用 composer，側邊欄就會閃出「Sign in」。 |
| **不**移植 desktop 的 `.normalize('NFKC')` | 它會**放寬**那個防止送出舊草稿的斷言，而 desktop 那個 helper 不是為 Meta 加的，沒有 Meta 證據。 |
| **不**把 `opacity: 0` 檢查加進 `src/content/base.ts` 的共用 `isVisible` | 該 helper 由 ChatGPT／Claude／Gemini／Grok 共用，目前都正常。只有 Meta 專屬的 `isVisibleMetaElement` 加了。 |
| `META_INPUT_SELECTORS` 保留最寬的 `[contenteditable="true"][role="textbox"]` | 查遍兩個 repo 都找不到任何一次實機命中紀錄；它是在 desktop `bd15628` 裡憑推測加的，當時的 debug bundle 沒有 DOM。沒有證據就無法安全縮小，所以留著，改由 probe 去取得答案。 |
| **DOM fixture 與單元測試不能記成 VM PASS** | 專案擁有者的明確規則。`store/META-AI-SMOKE.md` 至今維持 NOT_RUN。 |

已知但刻意保留的缺口：Meta 的 input 查找走共用的 `requireVisibleInput`，所以一個本身 `opacity: 0` 的 composer 仍可能被選成輸入目標。要動共用程式碼之前，需要實機證據。

## 最大的未爆彈

**Meta 從頭到尾沒有做過任何實機驗證，而它現在在所有使用者的瀏覽器裡。**

這是專案擁有者在 2026-09-22 明確決定的：不以實機測試作為發版門檻，改以使用者回報處理。發版本身沒有問題，但接手的人必須知道這件事的狀態：

- 認證後的 Meta 送出／接收，**從未**在真實登入頁面上跑過一次。
- 權限提示泡泡、動態 content script 註冊、瀏覽器重啟後的持久性，都只有單元測試覆蓋，沒有瀏覽器實測。
- `store/META-AI-SMOKE.md` 的每一項維持 **NOT_RUN**。這是刻意的：如果之後有人回報 Meta 故障，紀錄上若寫著 PASS，就無法分辨那是迴歸還是從來沒通過過。

**有人回報問題時的最快診斷路徑：** 用 `store/META-AI-STEP3-PROBE.js`（已隨 #47 的 gate 修正同步更新）。在已登入的 meta.ai 分頁跑一次，它會一次回答兩個到現在仍懸著的問題：那個最寬的 selector 到底有沒有命中真實節點，以及 `opacity: 0` / `data-disabled` 這兩個新 gate 在真實頁面上會不會誤擋。probe 只回傳 metadata（長度、布林值、tag、role、testId、aria-label），不回傳頁面文字內容。

## 三個會反覆咬人的陷阱

1. **這個 repo 沒有設定 git identity**，local 和 global 都沒有。`git commit` 會直接失敗。每次都要明確帶入以符合既有歷史：
   `git -c user.name="Theodore Huang" -c user.email="ted@ted-h.com" commit ...`

2. **「版號」在這個 repo 指兩件不同的事。** `package.json`／`package-lock.json`（兩處）／`public/manifest.json`／`dist/manifest.json` 是 **source** 版號，由 `scripts/check-version.js` 把關。但五個 README 和 `site/` 底下引用的是**已發布產物**的版號——下載連結、checksum 指令、「What changed in vX.Y.Z」。在 GitHub Release 實際存在之前就改後者，會產生死連結。

3. **商店的 ZIP 和 GitHub Release 的 ZIP 永遠不會有相同的 SHA-256，這是正常的。** `zip -r` 會把每個檔案的 mtime 寫進檔頭，所以手動打包的 ZIP 和 workflow 在乾淨 checkout 上建的 ZIP，即使內容逐位元組相同，容器 metadata 也不同。v0.3.0：GitHub asset `d7e97687…`，runner／商店 `57c1157a…`，但解壓後 `diff -r` 與逐檔 `sha256sum` 都完全相符。
   **不要把它當成第 1 點那個「兩個不同 build 共用一個版號」的 bug。** 確認方式很便宜：`gh run download <run-id>`，解開兩個壓縮檔，`diff -r` 加逐檔 `sha256sum`。README／`site/` 上的 checksum 必須維持 **GitHub asset** 的 hash，因為那才是使用者實際下載並驗證的檔案。詳見 `store/SUBMISSION.md` §6。

## 發布流程實際怎麼跑

1. bump source 版號並重建 `dist/`（`dist/` 有進版控，`npm run verify` 會重建它）。
2. 打包：`(cd dist && zip -qr <archive> .)`，ZIP 根目錄要有 `manifest.json`。
3. `gh release create vX.Y.Z --target <master SHA>`，附上 ZIP 與 `.sha256` 兩個 asset。
4. **這之後**才更新 README／`site/` 的下載連結（否則是死連結）。
5. Chrome Web Store：Actions → **Chrome Web Store** workflow（`workflow_dispatch`），version 填 `X.Y.Z`，模式選 `status-only` / `upload-only` / `staged` / `automatic`。

該 workflow 的 `chrome-web-store` environment 有 **required-reviewer 閘門**，指定 reviewer 是專案擁有者。所有模式（含 `status-only`）都會停下來等人工核准。
**那個閘門不要代按。** 即使 token 技術上可以（`current_user_can_approve: true`），它是擁有者自己加在發布環境上的人工檢查點。

Workflow 自身的保險：重跑 verify、確認 committed `dist/` 是最新的、驗證 ZIP 內 manifest 版號、拒絕覆蓋已在 `PENDING_REVIEW`／`STAGED` 的送審、拒絕版號沒有變大的上傳。
